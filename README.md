# Spooler Lab

เว็บจำลองระบบจัดคิวงานพิมพ์ที่พัฒนาจาก `print_spooler_v2.c` พร้อมคำอธิบายภาษาไทย สำหรับใช้ทดลองและนำเสนอในทีม กติกาปัจจุบันใช้ **เลข priority น้อยสำคัญกว่า: P1 สูงสุด และ P5 ต่ำสุด** โดยปรับทั้งเว็บและไฟล์ C ในโปรเจกต์ให้ตรงกัน พัฒนาด้วย HTML, JavaScript และ Tailwind CSS 4 โดยปรับหน้าตาจาก template **Simple Light ของ Cruip** ให้เข้ากับงาน Print Spooler และใช้ Node.js เปิดเว็บในเครื่อง

## เริ่มใช้งานแบบเร็ว

**เปิดเว็บเพื่อทดลองหรือนำเสนอ:** ถ้ามี Node.js และ npm อยู่แล้ว ให้เปิด Terminal ในโฟลเดอร์ที่มี `package.json` แล้วรัน:

```sh
npm start
```

เมื่อเห็น `Local: http://127.0.0.1:4173` ให้เปิด [เว็บจำลองในเครื่อง](http://127.0.0.1:4173) ด้วยเบราว์เซอร์ เก็บ Terminal นี้เปิดไว้ระหว่างใช้งาน และกด `Ctrl + C` เมื่อต้องการปิดเซิร์ฟเวอร์

โปรเจกต์เก็บไฟล์เว็บและ CSS ที่คอมไพล์แล้วไว้ใน `dist/` จึงเปิดเว็บด้วย `npm start` ได้ทันที แม้ยังไม่ได้ติดตั้ง dev dependencies คำสั่งนี้ทำหน้าที่เปิดเซิร์ฟเวอร์เท่านั้น ไม่ได้คอมไพล์ Tailwind CSS ให้

**เตรียมเครื่องเพื่อแก้หน้าตาเว็บ:** ติดตั้งแพ็กเกจตาม `package-lock.json` แล้วคอมไพล์ CSS ก่อนเปิดเว็บ:

```sh
npm ci
npm run build
npm start
```

`npm ci` ใช้อินเทอร์เน็ตเพื่อดาวน์โหลดเครื่องมือพัฒนา และ `npm run build` สร้าง `dist/styles.css` จาก `src/styles.css` ใช้สองคำสั่งนี้เมื่อเริ่มพัฒนา หรือหลังรับการเปลี่ยนแปลงแพ็กเกจ/CSS จากเพื่อน ส่วนการแก้ CSS ต่อเนื่องให้ใช้ `npm run dev:css` ตามหัวข้อ 5

## 4. วิธีทดลองสำหรับการสาธิตในทีม

**กติกาเลือกงาน:** Printer ที่ว่างเลือกงานจริงที่มี effective priority เป็นตัวเลขน้อยที่สุด หากเท่ากันจะเลือกงานที่เข้าคิวก่อน เมื่อเปิด Aging ใช้สูตร:

```text
effective_priority = priority - floor(wait_ms / 2000)
```

ค่าตัวเลขลดทุก 2 วินาทีเพื่อให้งานรอนานมีความสำคัญสูงขึ้น โดยไม่เปลี่ยน priority เดิม ตัวอย่างงาน P5:

| เวลารอ | Effective priority |
| --- | --- |
| 1,999 ms | 5 |
| 2,000 ms | 4 |
| 6,000 ms | 2 |

ค่าที่มีผลไม่จำกัดค่าต่ำสุด จึงเป็น 0 หรือติดลบได้ เช่น P1 รอ 4 วินาทีมีค่า -1 ตัวอย่างกรณีเท่ากัน: P5 รอ 8 วินาทีมีค่า 1 เท่ากับ P1 ที่เพิ่งเข้าคิว ระบบเลือก P5 ที่รอนานกว่าก่อน แต่เมื่อปิด Aging จะเลือก P1

**SHUTDOWN:** แยกด้วย `id = -1` และเลือกหลังงานจริงในคิวเสมอ ไม่ใช้ค่าที่มีผล -1 เป็นสัญญาณปิด ใน C งานพิเศษยังมี `priority = -1` แต่ `effective_priority()` คืน `INT_MAX` ส่วนเว็บใช้ `Infinity` จึงแยกจากงานจริงที่ได้ค่าติดลบจาก Aging

1. ที่แท็บ **ห้องทดลอง** เลือกจำนวนเครื่องพิมพ์ 1–4 เครื่อง และเปิดหรือปิด **Aging** ก่อนเริ่ม
2. กด **เริ่มจำลอง** เพื่อให้ Producer 4 ตัวส่งงานตัวละ 5 ชิ้น รวม 20 งาน เข้าคิวร่วมที่มีความจุ 10 ช่อง
3. ดูงานในคิว งานที่เครื่องพิมพ์กำลังทำ และบันทึกเหตุการณ์ด้านล่าง
4. กด **หยุดชั่วคราว** แล้วกด **ทีละขั้น** เพื่อเดินไปยังเวลาที่มีเหตุการณ์ถัดไป เหตุการณ์ที่เกิดพร้อมกันจะอยู่ในขั้นเดียวกัน
5. เปลี่ยน **ความเร็ว** ได้ระหว่างทดลอง โดยไม่เปลี่ยนกติกาหรือผลของเวลาจำลอง
6. รอจนแสดง **จำลองเสร็จสิ้น** ตรวจว่างานพิมพ์เสร็จครบ 20 งาน แล้วดูเวลารอเฉลี่ย เวลารอสูงสุด และการแบ่งงานของแต่ละเครื่อง
7. กดปุ่ม **↺ เริ่มต้นใหม่** ก่อนเปลี่ยนจำนวนเครื่องพิมพ์หรือ Aging การเริ่มใหม่ล้างผลรอบก่อน จึงควรจดหรือถ่ายภาพผลที่ต้องการเปรียบเทียบไว้ก่อน

ตัวอย่างการเปรียบเทียบที่แนะนำ:

| รอบ | เครื่องพิมพ์ | Aging | สิ่งที่สังเกต |
| --- | --- | --- | --- |
| 1 | 1 เครื่อง | เปิด | เลข effective priority ของงานรอนานลดลงทุก 2 วินาที จึงมีความสำคัญสูงขึ้น |
| 2 | 1 เครื่อง | ปิด | ลำดับงาน P5 ที่มีความสำคัญต่ำสุดและเวลารอเปลี่ยนไปอย่างไร |
| 3 | 4 เครื่อง | เปิด | การพิมพ์พร้อมกันช่วยระบายคิวและเปลี่ยนเวลารวมอย่างไร |

ทุกครั้งที่เริ่มใหม่ใช้ seed 42 จึงได้ข้อมูลชุดเดิมเพื่อเปรียบเทียบการตั้งค่า แต่ลำดับการรับงานอาจเปลี่ยนไปตามจำนวนเครื่องและ Aging อย่าสรุปล่วงหน้าว่าเปิด Aging แล้วเวลารอเฉลี่ยต้องลดลงทุกกรณี

สถิติ “งานที่ได้ Aging” นับเมื่อ `eff < priority` ตอนเริ่มพิมพ์ ตารางและกราฟแยกตาม **priority เดิม (base priority) P1–P5** ไม่ใช้ค่าที่ลดลงจาก Aging หากทั้งค่า effective และเวลาเข้าคิวตรงกันถึงมิลลิวินาที จะเลือกงานที่พบก่อนในอาร์เรย์ ซึ่งไม่รับประกัน FIFO อย่างเคร่งครัดหลังการสลับงานท้ายมาทับ

อีกสองแท็บใช้สำหรับอธิบายประกอบการนำเสนอ:

- **เข้าใจโปรแกรม:** บทอธิบายภาษาไทย 9 ส่วน ครอบคลุมโครงสร้างข้อมูล Priority, Aging, Semaphore, Shared Memory, Process และสถิติ
- **สำรวจโค้ด:** อ่านไฟล์ C เวอร์ชันปัจจุบันของโปรเจกต์ เลือกข้ามไปยังฟังก์ชันที่สนใจ และดาวน์โหลดไฟล์ได้

## 5. แก้โค้ดและตรวจงานก่อนส่งให้ทีม

### ติดตั้งเครื่องมือและคอมไพล์ CSS

ก่อนแก้หน้าตาเว็บ ให้รันในโฟลเดอร์ที่มี `package.json`:

```sh
npm ci
npm run build
```

- `npm ci` ติดตั้ง Tailwind CSS และ CLI ตามเวอร์ชันใน `package-lock.json` เหมาะสำหรับให้ทุกคนในทีมใช้ชุดแพ็กเกจเดียวกัน หากมี `node_modules/` เดิม คำสั่งจะติดตั้งใหม่ตาม lockfile
- `npm run build` คอมไพล์และย่อ CSS จาก `src/styles.css` ไปยัง `dist/styles.css` โดยอ่าน class ที่ใช้อยู่ใน HTML และ JavaScript ของเว็บ
- แก้สี ฟอนต์ ระยะห่าง และ responsive layout ใน **`src/styles.css`** แล้ว build ใหม่ ไม่ควรแก้ `dist/styles.css` โดยตรง เพราะจะถูกเขียนทับเมื่อคอมไพล์ครั้งถัดไป
- หากเพิ่มหรือเปลี่ยน Tailwind class ใน `dist/index.html`, `dist/app.mjs` หรือ `dist/guide.mjs` ต้องคอมไพล์ CSS ใหม่ด้วย

**Terminal 2 — เปิดเซิร์ฟเวอร์สำหรับเบราว์เซอร์**

### ตรวจงานก่อนส่งให้ทีม

รันคำสั่งต่อไปนี้หลังแก้เสร็จ:

```sh
npm run build
npm test
npm run check
```

- `npm run build` อัปเดตไฟล์ CSS ที่ใช้เปิดเว็บจริง ส่ง `dist/styles.css` ที่สร้างใหม่พร้อมกับไฟล์ต้นฉบับ เพื่อให้เพื่อนเปิดเว็บได้ทันที
- `npm test` ตรวจตรรกะของแบบจำลอง เช่น ขอบเขต Aging, การเลือกเลข priority น้อยก่อน, การเลือกงานเมื่อระดับเท่ากัน, คิวเต็ม, งานไม่หายหรือซ้ำ, สถิติ และการแยก sentinel ออกจากงานจริงที่มีค่าระดับติดลบ
- `npm run check` ตรวจ syntax ของ `dist/app.mjs`, `dist/engine.mjs` และ `dist/guide.mjs`

หากมี GCC บน Linux หรือ WSL ให้ตรวจฟังก์ชัน C ด้วยคำสั่งต่อไปนี้จากโฟลเดอร์โปรเจกต์:

```sh
mkdir -p .sites-runtime/c-check
gcc -Wall -Wextra -Werror -o .sites-runtime/c-check/priority_c_test tests/priority_c_test.c -lrt -lpthread
./.sites-runtime/c-check/priority_c_test
```

ควรแสดง `C priority regression tests: 7 passed` ชุดทดสอบนี้เรียกฟังก์ชันจากไฟล์ C ในโปรเจกต์โดยตรง เพื่อตรวจ P1 ได้ก่อน, Aging, การตัดสินกรณีเท่ากัน, SHUTDOWN และสถิติ โดยไม่เรียก `main()` ของโปรแกรมหรือสร้าง process ลูก

ตรวจหน้าเว็บทั้งบนจอกว้างและจอมือถือ รวมถึงลองเริ่มจำลอง หยุด ทีละขั้น และเปิดแท็บบทอธิบาย/โค้ด หลังแก้ HTML หรือ JavaScript ให้บันทึกแล้วรีเฟรชเบราว์เซอร์ ส่วน CSS ต้องคอมไพล์ก่อนรีเฟรช การรีเฟรชจะเริ่มสถานะการจำลองใหม่ หากแก้ `server.mjs` ให้หยุดเซิร์ฟเวอร์ด้วย `Ctrl + C` แล้วเปิดใหม่

## 7. รันโปรแกรม C ของโปรเจกต์แยกต่างหาก (ไม่บังคับ)

ส่วนนี้ใช้เมื่อต้องการดูผลจาก POSIX จริง โดยไฟล์ `dist/print_spooler_v2.c` และไฟล์ที่ดาวน์โหลดจากเว็บเป็นเวอร์ชันปรับให้ P1 สำคัญสูงสุด ใช้ Aging ลบค่าและตรวจ SHUTDOWN ด้วย id ต้องมี **Linux หรือ Linux ใน WSL พร้อม GCC** และรันคำสั่งใน Terminal ของ Linux ไม่ใช่ PowerShell โดยตรง

เข้าโฟลเดอร์โปรเจกต์จากฝั่ง Linux แล้วทำตามนี้:

```sh
cd dist
gcc -Wall -o spooler_v2 print_spooler_v2.c -lrt -lpthread

./spooler_v2       # 1 เครื่อง เปิด Aging
./spooler_v2 2 1   # 2 เครื่อง เปิด Aging
./spooler_v2 1 0   # 1 เครื่อง ปิด Aging
```

รันทีละคำสั่งและรอให้แต่ละรอบจบ โปรแกรมจะแสดงสถิติใน Terminal และสร้าง `spooler_log.txt` ในโฟลเดอร์ที่รัน โดยลบ log เก่าก่อนเริ่มรอบใหม่ หากต้องการเก็บผลเปรียบเทียบให้สำรอง log ก่อนรันครั้งถัดไป และไม่ควรเปิดโปรแกรม C หลายอินสแตนซ์พร้อมกันเพราะใช้ชื่อ shared memory กับชื่อ log เดียวกัน

## ขอบเขตของเว็บจำลอง

เว็บจำลองพฤติกรรมด้วย JavaScript ไม่ได้เรียก `fork()`, `mmap()` หรือ POSIX semaphore จริง และไม่ใช่ benchmark ของโปรแกรม C

เมื่อเหตุการณ์มีเวลาเท่ากัน เว็บประมวลผลการพิมพ์เสร็จ Producer ตามหมายเลข และ Printer ตามหมายเลข คิวใช้การสแกนเลือกงานจริงที่มีค่าระดับน้อยที่สุดและสลับงานท้ายตามโค้ด C ในโปรเจกต์ ค่า semaphore บนเว็บเป็นสถานะหลังจบเหตุการณ์ จึงไม่แสดงช่วงล็อกระหว่างคำสั่ง

สถิติใน C ถูกบันทึกตอนเริ่มพิมพ์ แม้ชื่อตัวแปรจะเป็น `jobs_done` เว็บจึงแยกจำนวน “เริ่มพิมพ์” กับ “พิมพ์เสร็จ” ให้ชัดเจน เวลารอไม่นับช่วงที่ Producer รอช่องว่างก่อนเข้าคิวและไม่นับเวลาพิมพ์

การจำลองทำงานในเบราว์เซอร์โดยไม่มีการส่งข้อมูลการจำลองไปยังเซิร์ฟเวอร์ และมี WebMCP แบบ optional สำหรับอ่านสถานะและเดินเหตุการณ์ในเบราว์เซอร์ที่รองรับ
