บทคัดย่อ

Print Spooler Simulation เป็นโครงการสาธิตการประสานงานระหว่างกระบวนการตามปัญหา Producer–Consumer ผู้สร้างงานหลายตัวส่งงานไปยังคิวร่วมที่มีความจุจำกัด และเครื่องพิมพ์หลายตัวดึงงานไปทำ โปรแกรมภาษา C ใช้ process, POSIX shared memory และ semaphore จริง ส่วนเว็บใช้ JavaScript จำลองกติกาและเวลาเพื่อให้ผู้เรียนติดตามเหตุการณ์ได้ง่าย

ระบบมี Producer 4 ตัว ตัวละ 5 งาน รวม 20 งาน คิวจุ 10 งาน และ Printer 1–4 ตัว การเลือกงานใช้ค่าความสำคัญที่ยิ่งน้อยยิ่งสำคัญ โดย P1 เป็นระดับเดิมที่สำคัญสูงสุด เมื่อเปิด Aging งานที่รอครบทุก 2 วินาทีจะมีค่าที่ใช้เลือกลดลง 1 หากค่าเท่ากันจะเลือกงานที่เข้าคิวก่อน โดยใช้เวลาและเลขลำดับเข้าคิวเป็นตัวตัดสิน

ประเด็นหลักของโครงการคือการรักษาความถูกต้องของข้อมูลร่วม การรอคิวโดยไม่ขัดขวางอีกฝ่าย การแยกความสำคัญเดิมออกจากค่าหลัง Aging และการปิดกระบวนการให้ครบ รายงานอธิบายโค้ดปัจจุบันซึ่งมีเลขลำดับเข้าคิวสำหรับรักษา FIFO แม้เวลาเข้าตรงกันถึงมิลลิวินาที รวมทั้งอธิบายข้อจำกัดของสถิติและแบบจำลองเว็บ

1 วัตถุประสงค์และขอบเขต

โปรแกรมแสดงให้เห็นว่าผู้ส่งงานหลายคนและเครื่องพิมพ์หลายเครื่องใช้คิวเดียวกันได้อย่างไร โดยต้องควบคุมทั้งการเข้าถึงข้อมูลและจำนวนงานในคิว การใช้เพียงตัวแปรนับงานไม่เพียงพอเมื่อหลาย process อาจอ่านและเขียนค่าเดียวกันในเวลาใกล้กัน

วัตถุประสงค์ของโครงการมีดังนี้

  • ศึกษา Producer–Consumer ที่มีคิวจำกัดความจุ
  • ใช้ shared memory ส่งต่อข้อมูลระหว่าง process
  • ใช้ semaphore ป้องกัน race condition และรอเงื่อนไขคิวเต็มหรือคิวว่าง
  • ทดลองกติกา Priority scheduling และ Aging
  • เปรียบเทียบจำนวนเครื่องพิมพ์ เวลารอ และการกระจายงาน
  • ใช้เว็บแสดงขั้นตอนและช่วยอธิบายความสัมพันธ์กับโค้ด C

การพิมพ์ในโครงการเป็นการพักเวลาตามจำนวนหน้า ไม่ได้เปิดอ่านไฟล์เอกสารหรือส่งข้อมูลไปยังเครื่องพิมพ์จริง ชื่อไฟล์ เช่น user3_doc0.txt เป็นข้อมูลในโครงสร้างงาน เว็บก็ไม่ได้เรียกใช้โปรแกรม C อยู่เบื้องหลัง

3 โครงสร้างข้อมูล

3.1 โครงสร้าง Job

Job แทนงานพิมพ์หนึ่งชิ้น โดยข้อมูลที่มีผลต่อการเลือกงานคือ Priority เดิม เวลาเข้าคิว และเลขลำดับเข้าคิว

ตารางที่ 2 ข้อมูลใน Job ของโปรแกรม C
ฟิลด์ ชนิดข้อมูล หน้าที่
id int รหัสงาน หรือ −1 สำหรับ SHUTDOWN
priority int ความสำคัญเดิม 1–5
pages int จำนวนหน้าที่ใช้คำนวณเวลาพิมพ์
filename char[64] ชื่อไฟล์ประกอบงาน
enqueue_ms long long เวลาเข้าคิวสำหรับคำนวณเวลารอและ Aging
enqueue_seq long long ลำดับเข้าคิวสำหรับตัดสินเมื่อเวลาเท่ากัน

รหัสงานคำนวณจาก producer_id * 100 + i โดย i เริ่มจาก 0 ถึง 4 ดังนั้น Producer 1 มีงาน #100–104 และ Producer 4 มีงาน #400–404 ตัวอย่าง #103 คือ Producer 1 งานที่ 4 ส่วน #401 คือ Producer 4 งานที่ 2 รหัสนี้ใช้ระบุตัวงาน ไม่ได้บอก Priority หรือลำดับที่จะได้พิมพ์

3.2 โครงสร้าง Stats

Stats เก็บผลสะสมร่วมของ Printer ทุกตัว มีจำนวนงาน เวลารอรวม เวลารอสูงสุด จำนวนงานที่ได้รับ Aging อาร์เรย์แยกตาม Priority และอาร์เรย์แยกตามเครื่องพิมพ์

ฟิลด์ jobs_done, total_wait_ms, max_wait_ms และ aged_jobs เป็นสถิติรวม ส่วน prio_count, prio_wait_ms, prio_max_ms จัดกลุ่มตาม Priority เดิม 1–5 โดยช่อง 0 ของอาร์เรย์ Priority ไม่ได้ใช้สำหรับงานจริง ฟิลด์ printer_jobs และ printer_pages เก็บงานกับจำนวนหน้าของแต่ละเครื่อง โดยเครื่องหมายเลข 1 ใช้อินเด็กซ์ 0

ชื่อ jobs_done ต้องอธิบายตามตำแหน่งเรียกจริง เพราะโค้ดเพิ่มค่านี้ก่อนพักเวลาจำลองพิมพ์ จึงนับงานที่เริ่มพิมพ์ระหว่างรัน เมื่อ Parent รอ Printer จบครบในการจบปกติ ค่านี้จึงตรงกับงานที่เสร็จแล้ว ประเด็นนี้ต่างจากเว็บที่แยก started และ completed

3.3 โครงสร้าง SharedQueue

SharedQueue รวม jobs[10], count, aging_enabled, next_seq, Stats และ semaphore 4 ตัวไว้ในพื้นที่ shared memory เดียวกัน ตัวนับ count คือจำนวนรายการที่รออยู่ในคิว ไม่รวมงานที่ Printer ดึงออกไปพิมพ์แล้ว แต่รวม SHUTDOWN ที่ยังอยู่ในคิว

next_seq เพิ่มภายใต้ mutex ทุกครั้งที่เข้าคิวสำเร็จ ทำให้แต่ละงานมีเลขลำดับไม่ซ้ำกัน ลำดับนี้หมายถึงการรับงานเข้าคิวสำเร็จ ไม่ใช่เวลาที่ Producer เริ่มเรียก enqueue ก่อนอาจถูกบล็อกเพราะคิวเต็ม

4 ลำดับการทำงานของโปรแกรม C

ฟังก์ชัน main() เป็นผู้จัดการวงจรชีวิตของระบบตามลำดับนี้

  1. ตั้ง stdout เป็นแบบไม่เก็บ buffer แล้วอ่านจำนวน Printer และตัวเลือก Aging ค่าเริ่มต้นคือ 1 เครื่องและเปิด Aging
  2. ตรวจจำนวน Printer ว่าอยู่ระหว่าง 1–4 แล้วลบ log เดิมและชื่อ shared memory เดิม
  3. สร้าง shared memory ปรับขนาด และ map เป็น SharedQueue
  4. กำหนดข้อมูลเริ่มต้นและสร้าง semaphore ทั้ง 4 ตัวให้ใช้ข้าม process ได้
  5. บันทึกเวลาเริ่ม แล้ว fork Producer 4 ตัว จากนั้น fork Printer ตามจำนวนที่เลือก
  6. รอ Producer ทั้งหมดจบด้วย waitpid() แล้วส่ง SHUTDOWN หนึ่งรายการต่อ Printer
  7. รอ Printer ทุกตัวจบ แล้วบันทึกเวลารวม
  8. อ่าน Stats และแสดงรายงาน
  9. ทำลาย semaphore, unmap พื้นที่ และ unlink ชื่อ shared memory

ลูกที่ fork สำเร็จจะเข้าสู่ run_producer() หรือ run_printer() และจบด้วย exit(0) จึงไม่กลับมาวนสร้างลูกต่อใน main การรอด้วย waitpid ทีละ PID ไม่ได้ทำให้ลูกทำงานทีละตัว เพราะลูกทุกตัวที่สร้างไปแล้วสามารถทำงานพร้อมกันได้ตามการจัดสรรของระบบปฏิบัติการ

5 Shared Memory และการสร้าง Process

ตัวแปรธรรมดาหลัง fork โดยทั่วไปอยู่ใน address space ของแต่ละ process การแก้ตัวแปรในลูกจึงไม่ใช่วิธีส่งข้อมูลร่วมกลับให้ Parent โปรแกรมนี้สร้าง mapping แบบ MAP_SHARED ก่อน fork เพื่อให้ทุกลูกเข้าถึงข้อมูลร่วมเดียวกัน

ขั้นแรก shm_open() สร้างวัตถุ POSIX shared memory และคืน file descriptor โปรแกรมใช้ O_CREAT | O_EXCL | O_RDWR เพื่อสร้างใหม่และเปิดอ่านเขียน จากนั้น ftruncate() กำหนดขนาดให้เท่ากับ sizeof(SharedQueue) เพราะวัตถุใหม่เริ่มจากขนาดศูนย์ แล้ว mmap() เชื่อมวัตถุเข้ากับ address space โดยอนุญาตอ่านเขียนและใช้ MAP_SHARED การปิด descriptor หลัง mmap ไม่ได้ยกเลิก mapping ที่สร้างแล้ว Linux man-pages shm_open

โปรแกรม initialize semaphore ในพื้นที่ร่วมก่อนสร้างลูก และส่งค่า pshared=1 ให้ sem_init() เพื่อใช้งานระหว่าง process หากใช้ pshared เป็น 0 จะเป็นการใช้ระหว่าง thread ภายใน process เดียว ซึ่งไม่ตรงกับโครงสร้างของงานนี้ Linux man-pages sem_init

6 Semaphore และการป้องกันปัญหาคิว

Race condition เกิดได้เมื่อสอง process เห็น count ค่าเดียวกันแล้วเขียนงานลงตำแหน่งเดียว หรือเมื่อ Printer สองตัวเลือกและนำงานเดียวกันออก ดังนั้นการอ่านแก้คิวต้องอยู่ใน critical section ที่มี mutex คุม ขณะเดียวกันต้องมีตัวนับสิทธิ์แยกสำหรับคิวเต็มและคิวว่าง

ตารางที่ 4 Semaphore ของระบบ
ชื่อ ค่าเริ่มต้น สิ่งที่ควบคุม
mutex 1 ให้แก้ jobs, count และ next_seq ทีละ process
empty_slots 10 จำนวนสิทธิ์เพิ่มงานในคิว

stats_lock 1 ให้ Printer แก้ Stats ทีละตัว

6.1 ฝั่ง Producer

Producer รอ empty_slots ก่อน เมื่อได้สิทธิ์เพิ่มงานแล้วจึงขอ mutex ประทับเวลาและเลขลำดับ วางงานท้ายคิว และเพิ่ม count จากนั้นปล่อย mutex แล้ว post filled_slots เพื่อแจ้งว่ามีงานให้ Printer รับได้

sem_wait(&q->empty_slots);
sem_wait(&q->mutex);
/* ประทับเวลาและ sequence แล้วต่อท้ายคิว */
sem_post(&q->mutex);
sem_post(&q->filled_slots);

6.2 ฝั่ง Printer

Printer รอ filled_slots เพื่อยืนยันว่ามีสิทธิ์รับงาน แล้วจึงขอ mutex สแกนเลือกงาน นำงานออก และลด count จากนั้นปล่อย mutex แล้ว post empty_slots เพื่อคืนช่องให้ Producer การจำลองพิมพ์เกิดหลังออกจาก critical section แล้ว

sem_wait(&q->filled_slots);
sem_wait(&q->mutex);
/* เลือกงานและนำออกจากคิว */
sem_post(&q->mutex);
sem_post(&q->empty_slots);

6.3 เหตุผลที่ต้องรอเงื่อนไขก่อนจับ mutex

หาก Producer จับ mutex ก่อนแล้วค่อยรอ empty_slots ขณะคิวเต็ม มันจะถือ mutex รอช่องว่าง ขณะที่ Printer ต้องได้ mutex เพื่อเอางานออก ทั้งสองฝ่ายจึงรอกันและเกิด deadlock ได้ ฝั่ง Printer ก็มีปัญหาแบบเดียวกันหากถือ mutex แล้วรอคิวที่ว่างให้มีงาน

การใช้ stats_lock แยกจาก queue mutex ทำให้การเก็บสถิติไม่ต้องล็อกคิวค้างไว้ และเวลาพิมพ์ก็ไม่อยู่ใต้ queue mutex จึงให้ Printer หลายตัวทำงานคนละชิ้นพร้อมกันได้

หลังจบ operation ทั้งหมด ค่าที่มองเห็นจะสอดคล้องกับช่องว่างและงานในคิว แต่ระหว่างจอง token ก่อนปรับคิวหรือก่อน post คืน ค่า semaphore อาจยังไม่ตรงกับ count จึงไม่ควรกล่าวว่า empty_slots + filled_slots = 10 ทุกขณะของการทำงานจริง เว็บแสดงภาพหลังเหตุการณ์และไม่ได้จำลองทุกช่วงย่อยเหล่านี้

7 Priority และ Aging

7.1 ความสำคัญเดิมและค่าที่ใช้เลือก

Priority เดิมอยู่ระหว่าง 1–5 โดย P1 สำคัญที่สุดและ P5 สำคัญน้อยที่สุด เมื่อปิด Aging ค่า effective เท่ากับ Priority เดิม เมื่อเปิด Aging ใช้กติกาต่อไปนี้

wait_ms = now_ms - enqueue_ms
effective = priority - floor(wait_ms / 2000)

สำหรับเวลารอที่ไม่ติดลบ การหารจำนวนเต็มใน C ให้ผลแบบเดียวกับ floor ค่าจะลดลงครั้งละ 1 เมื่อรอครบอีก 2000 ms ดังนั้นงานเก่ามีโอกาสแข่งขันกับงานใหม่มากขึ้น โดยไม่ได้เปลี่ยน Priority เดิมที่เก็บไว้

ตารางที่ 5 ตัวอย่างงานที่มี Priority เดิม P5 เมื่อเปิด Aging
เวลารอ จำนวนช่วงที่ครบ Effective
0–1999 ms 0 5
2000–3999 ms 1 4
4000–5999 ms 2 3
6000–7999 ms 3 2
8000–9999 ms 4 1
10000–11999 ms 5 0

โค้ดไม่จำกัดค่าต่ำสุด งานจริงจึงมี effective เป็นศูนย์หรือติดลบได้ เช่น P1 รอ 4000 ms ได้ effective −1 งานนี้ยังเป็นงานปกติ เพราะระบบแยก SHUTDOWN ด้วย ID ไม่ได้ตรวจจาก effective

7.2 ลำดับการตัดสินใจล่าสุด

ระบบเลือก effective ต่ำสุดก่อน ถ้าเท่ากันเลือก enqueue_ms ที่น้อยกว่า หากเวลาตรงกันถึงมิลลิวินาทีจึงเลือก enqueue_seq ที่น้อยกว่า หมายความว่า FIFO ใช้ตัดสินระหว่างงานที่มี effective เท่ากัน ไม่ใช่ว่าทุกงานต้องพิมพ์ตามเวลามาถึงโดยไม่สนใจ Priority

ตัวอย่าง งาน A มี P5 และรอ 8 วินาที จะได้ effective 1 เท่ากับงาน B ที่เป็น P1 และเพิ่งเข้าคิว ระบบเลือก A เพราะ A เข้าคิวก่อน หากปิด Aging ระบบเลือก B เพราะ 1 น้อยกว่า 5

เลขลำดับเข้าคิวถูกเพิ่มขณะถือ mutex จึงใช้รักษา FIFO ในกรณีเวลาเท่ากันได้ แม้การนำงานออกจะย้ายงานท้ายอาร์เรย์มาทับช่องที่ว่าง ตำแหน่งในอาร์เรย์ไม่ใช่ตัวตัดสินลำดับสุดท้ายของโค้ดปัจจุบัน

7.3 สิ่งที่ Aging รับรองไม่ได้จากผลรันครั้งเดียว

Aging มีเป้าหมายเพิ่มโอกาสให้งานที่รอนาน ไม่ใช่การหาค่าเฉลี่ยเวลารอต่ำสุด จึงไม่รับประกันว่าเปิดแล้วค่าเฉลี่ยของทุกชุดงานจะลดลง และ P1 ก็ไม่จำเป็นต้องมีค่าเฉลี่ยต่ำสุดทุกครั้ง เพราะเวลาที่งานมาถึง งานที่กำลังพิมพ์ และ Aging มีผลร่วมกัน

โปรแกรมนี้มีงานเพียง 20 ชิ้นและเวลาพิมพ์จำกัด เมื่อระบบทำงานปกติ งานจึงระบายครบได้แม้ปิด Aging การทดลองนี้ช่วยเห็นกลไกลดการถูกแซง แต่ไม่ใช่ข้อพิสูจน์เรื่อง starvation สำหรับระบบที่มีงานใหม่เข้าตลอดไป

Printer ทำงานแบบ non-preemptive เมื่อเริ่มงานแล้วจะพิมพ์ต่อจนจบ งานสำคัญกว่าที่เพิ่งมาไม่แทรกกลางงานที่กำลังพิมพ์

8 การเพิ่มและนำงานออกจากคิว

8.1 การจัดเก็บและประสิทธิภาพ

enqueue ต่อท้าย jobs[count++] จึงใช้เวลา O(1) สำหรับการแก้อาร์เรย์เมื่อได้สิทธิ์แล้ว ส่วน dequeue ต้องสแกนงานทั้งหมดเพื่อหา effective ต่ำสุด ใช้ O(n) โดย n ไม่เกิน 10 หลังพบเป้าหมายจะนำงานท้ายสุดมาทับช่องของเป้าหมาย แล้วลด count จึงลบได้ O(1) โดยไม่เลื่อนงานทั้งหมด

การเรียงคิวครั้งเดียวตอนรับเข้าไม่เพียงพอสำหรับการใช้ค่าหลัง Aging เพราะ effective เปลี่ยนตามเวลารอ การคำนวณตอน dequeue ทำให้ใช้ค่าปัจจุบันในการตัดสินใจ และต้นทุนสแกนเหมาะกับคิวขนาดเล็กของโครงการ

8.2 ตัวอย่างการสลับตำแหน่ง

สมมติอาร์เรย์เก็บ [A, B, C, D] และเลือก B ไปพิมพ์ โปรแกรมจะนำ D มาแทนช่องของ B เหลือ [A, D, C] แม้ C อาจเข้ามาก่อน D ก็ตาม การเก็บข้อมูลแบบนี้ยังเลือกงานได้ถูกต้อง เพราะการตัดสินใจพิจารณา Priority เวลา และ sequence ไม่ได้เลือกช่องซ้ายสุดเสมอ

8.3 มุมมองสองแบบบนเว็บ

แถวช่องด้านบนที่ชื่อ ลำดับเข้าคิว เรียงเฉพาะงานที่ยังรออยู่ตามเวลาและ sequence จากซ้ายไปขวา ส่วนตาราง ลำดับเลือกพิมพ์ ณ ตอนนี้ ใช้ Priority/Aging และกติกานำงานออกบนสำเนาข้อมูล ทั้งสองมุมมองไม่เปลี่ยนคิวต้นฉบับ

ตารางเลือกงานคำนวณด้วยเวลาปัจจุบันคงที่ จึงบอกอันดับ ณ ตอนนั้น ไม่ใช่คำรับประกันลำดับพิมพ์ทั้งหมดในอนาคต งานใหม่ที่เข้ามาและเวลารอที่เพิ่มขึ้นอาจเปลี่ยนผลการเลือกครั้งถัดไปได้

ตัวอย่างจากเว็บรุ่นปัจจุบัน ใช้ seed 42, Printer 1 ตัว และเปิด Aging ที่เวลา 400 ms จะเริ่มพิมพ์ #300 แล้ว งานที่เหลือมีลำดับเข้าคิว #100 → #400 → #101 → #401 ส่วนลำดับเลือก ณ ตอนนั้นคือ #400 → #100 → #101 → #401 ตัวอย่างนี้เป็นผลของแบบจำลองเว็บ ไม่ใช่ log จากการสุ่มของ C

9 ฟังก์ชันทั้งหมดของโปรแกรม C

ตารางที่ 6 หน้าที่และความสัมพันธ์ของฟังก์ชัน
ฟังก์ชัน หน้าที่หลัก ผู้เรียกหรือข้อมูลที่เกี่ยวข้อง
now_ms อ่าน CLOCK_MONOTONIC แล้วแปลงเป็น ms ใช้ประทับเวลา คำนวณเวลารอ และเวลารวม
log_line จัดข้อความพร้อมเวลาและ PID แล้วเขียน log กับ stdout Parent, Producer และ Printer
effective_priority คำนวณ Priority หลัง Aging และแยก sentinel เรียกขณะ dequeue สแกนคิว
enqueue รอช่อง ล็อก ประทับเวลาและ sequence แล้วต่อท้าย Producer และ Parent ที่ส่ง SHUTDOWN
dequeue รอให้มีงาน เลือกตามกติกา แล้วนำออก Printer รับ Job พร้อม effective และ wait
record_stats เพิ่มจำนวนงาน เวลา และสถิติแต่ละกลุ่ม Printer เรียกก่อนจำลองพิมพ์
run_producer สุ่มและส่ง 5 งาน แล้วจบ process ลูกฝั่ง Producer
run_printer รับงาน พิมพ์ หรือหยุดเมื่อรับ sentinel ลูกฝั่ง Printer
print_report อ่านและพิมพ์สถิติหลังลูกจบครบ Parent
main ตั้งระบบ สร้างลูก รอ ปิดระบบ และคืนทรัพยากร จุดเริ่มต้นของโปรแกรม

9.1 เวลาและข้อความ

now_ms() ใช้ CLOCK_MONOTONIC สำหรับวัดระยะเวลา แทนการนำเวลาปฏิทินมาใช้คำนวณ Aging จึงไม่กระโดดตามการตั้งเวลานาฬิกาปฏิทินโดยตรง ส่วน log_line() ใช้เวลาท้องถิ่นรูปแบบชั่วโมง นาที วินาทีเพื่อให้คนอ่านได้สะดวก สองอย่างนี้มีหน้าที่ต่างกัน Linux man-pages clock_gettime

log_line() รับอาร์กิวเมนต์แบบ variadic ผ่าน va_list จัดข้อความด้วย vsnprintf แล้วเพิ่มเวลาและ PID ก่อนเขียนไฟล์ ช่วยให้แต่ละ process ใช้รูปแบบบันทึกเดียวกัน setvbuf() ใน main ปิด stdout buffering เพื่อลดปัญหาข้อความใน buffer ถูกสำเนาไปกับ fork แล้วถูกพิมพ์ซ้ำภายหลัง

9.2 Producer

run_producer() ตั้ง seed ของ rand จาก PID XOR เวลาปัจจุบัน จากนั้นสร้าง Job จำนวน 5 ชิ้นด้วยรหัสและชื่อไฟล์ที่สัมพันธ์กับ Producer สุ่ม Priority 1–5 และหน้า 1–8 เรียก enqueue แล้วเขียน log หลังส่งสำเร็จ ก่อนพัก 100–499 ms ทุกครั้ง รวมหลังส่งงานชิ้นสุดท้าย จากนั้น exit

การพักหลังงานสุดท้ายทำให้ Parent ยังต้องรอ Producer แม้มันส่งครบแล้ว จึงมีผลต่อเวลาส่ง SHUTDOWN และเวลารวมเมื่อคิวระบายเร็วกว่าการจบ Producer

9.3 Printer และการส่งค่ากลับจาก dequeue

run_printer() วนเรียก dequeue ซึ่งคืน Job และเขียน effective กับเวลารอผ่านพอยน์เตอร์ out_eff และ out_wait ทำให้ผู้เรียกได้ทั้งงานและค่าที่ใช้ตัดสิน ณ เวลานั้นโดยไม่ต้องคำนวณซ้ำภายหลัง

หาก ID เป็น −1 จะเขียน log แล้วออกจาก loop หากเป็นงานจริงจะเขียน log เริ่มพิมพ์ เรียก record_stats พักเวลา pages * 200 ms และเขียน log พิมพ์เสร็จ การพิมพ์และ logging ไม่ครอบด้วย queue mutex

9.4 การบันทึกและอ่านสถิติ

record_stats() จับ stats_lock ก่อนเพิ่มจำนวนงาน รวมเวลารอ อัปเดตค่าสูงสุด ตรวจว่า effective ต่ำกว่า Priority เดิมหรือไม่ และเพิ่มอาร์เรย์ตาม Priority กับเครื่องพิมพ์ จากนั้นคืน lock

print_report() เรียกหลังรอ Printer ทุกตัวจบ จึงอ่าน Stats ได้โดยไม่มี Printer มาแก้ค่าแข่งอีก แสดงจำนวนงาน เวลารวม ค่าเฉลี่ย ค่าสูงสุด จำนวนงานที่ได้รับ Aging สถิติราย Priority และจำนวนงานกับหน้าของแต่ละเครื่อง

10 สถิติ เวลา และบันทึกเหตุการณ์

10.1 ความหมายของเวลารอ

เวลารอที่เก็บคือเวลาปัจจุบันที่ dequeue ใช้เลือก ลบด้วย enqueue_ms ซึ่งประทับหลัง Producer ได้ช่องว่างและ mutex แล้ว เวลานี้จึงวัดการรอในคิว ไม่รวมการรอ empty_slots ก่อนเข้าคิว และไม่รวมเวลาพิมพ์ ส่วนงานจริงใน C ยังมีต้นทุนการสแกน การเขียน log และขั้นตอนก่อน usleep เพิ่มจากจุดประทับเวลานั้น

เวลารอเฉลี่ย = เวลารอรวมของงานที่บันทึก / จำนวนงานที่บันทึก
เวลาพิมพ์จำลอง = จำนวนหน้า * 200 ms
เวลารวม = เวลาหลังรอ Printer ครบ - เวลาก่อนเริ่ม fork

เวลารวมเป็นระยะเวลาที่ระบบทำงานผ่านไป ไม่ใช่ CPU time รวมการสร้างลูก ช่วงมาถึงงาน การรอ การเขียน log การพักจำลองพิมพ์ และช่วงปิดระบบ ไม่รวมการเตรียม shared memory ก่อนจับเวลา และไม่รวมการแสดงรายงานกับ cleanup หลังจับเวลาสิ้นสุด

10.2 การอ่านสถิติอย่างถูกต้อง

กราฟราย Priority จัดกลุ่มด้วย Priority เดิม แม้งาน P5 ได้ effective 1 ก็ยังอยู่กลุ่ม P5 กราฟ เวลารอเฉลี่ยเมื่อเริ่มพิมพ์ คิดเฉพาะงานที่ Printer รับไปเริ่มแล้ว โดยบันทึกเวลารอของแต่ละงานครั้งเดียว ค่าเฉลี่ยของกลุ่มจึงเปลี่ยนเมื่อมีงานกลุ่มนั้นเริ่มพิมพ์เพิ่มเติม การคงค่าเดิมระหว่างรอไม่ใช่อาการโปรแกรมค้าง

เว็บแยกกราฟ เวลารอเฉลี่ยของงานในคิว (สด) สำหรับงานที่ยังรออยู่ ค่าเฉลี่ยคำนวณจาก เวลาจำลองปัจจุบัน - เวลาเข้าคิว ของงานในกลุ่มนั้น จึงเพิ่มตามนาฬิกาจำลองเมื่อสมาชิกกลุ่มเดิมยังอยู่ และอาจเพิ่มหรือลดเมื่อมีงานเข้า–ออก เครื่องหมาย — หมายถึงไม่มีงานในกลุ่มที่กราฟนั้นนับ เมื่อกดหยุดชั่วคราว นาฬิกาจำลองและกราฟสดจะหยุดด้วย

aged_jobs เพิ่มเมื่อ effective ต่ำกว่า Priority เดิม ณ ตอนเริ่มพิมพ์ เป็นจำนวนงานที่ค่าความสำคัญถูกปรับด้วย Aging ไม่ใช่จำนวนครั้งที่ปรับ และไม่พิสูจน์ว่างานนั้นรอเร็วขึ้นเมื่อเทียบกับการปิด Aging แม้งานเดียวในคิวก็อาจถูกนับได้

สถิติจำนวนงานแต่ละ Printer ไม่จำเป็นต้องเท่ากัน งานมีจำนวนหน้าต่างกันและเครื่องว่างต่างเวลา จึงควรดูทั้งจำนวนงาน จำนวนหน้า และเวลารวม ไม่สรุปประสิทธิภาพจากจำนวนงานอย่างเดียว

10.3 ข้อจำกัดของ log

Producer เขียน log หลัง enqueue ปล่อย mutex และแจ้ง filled_slots แล้ว Printer จึงอาจรับงานและเขียน log เริ่มพิมพ์ก่อน Producer เขียน log ส่งงานของชิ้นเดียวกันได้ ลำดับบรรทัดที่เห็นจึงไม่ใช่หลักฐานลำดับเข้าคิวที่แม่นยำเสมอ

การเปิดไฟล์ด้วย O_APPEND ทำให้การเลื่อนไปท้ายไฟล์และการ write เป็นขั้นตอน atomic ตามเงื่อนไขของระบบ แต่ไม่รับประกันลำดับเหตุการณ์ระหว่าง process ไม่รับประกัน stdout จะเรียงตรงกับไฟล์ และไม่แทนการตรวจ partial write หรือ error โดยเฉพาะบน filesystem ที่มีข้อจำกัด เช่น NFS Linux man-pages open, write

11 การปิดระบบและคืนทรัพยากร

Parent รอ Producer ทุกตัวจบก่อน จึงทราบว่าจะไม่มีงานจริงใหม่จาก Producer จากนั้นส่งงานพิเศษ SHUTDOWN จำนวนเท่ากับ Printer แต่ละตัวรับหนึ่งรายการแล้วออกจาก loop หากส่งเพียงรายการเดียวเมื่อมีหลาย Printer บางเครื่องอาจค้างรอ filled_slots ต่อไป

sentinel มี ID −1, Priority −1, หน้า 0 และชื่อ SHUTDOWN แต่ effective_priority() ตรวจ ID แล้วคืน INT_MAX ให้ทันที ทำให้มันถูกเลือกหลังงานจริงในคิวและไม่ได้รับ Aging เว็บใช้ Infinity เพื่อให้ผลเปรียบเทียบแบบเดียวกัน

Printer หนึ่งตัวอาจหยุดแล้วขณะที่อีกตัวกำลังพิมพ์งานจริงที่ดึงออกจากคิวไปก่อนหน้า การที่คิวไม่มีงานจริงเหลือจึงไม่แปลว่าทุกเครื่องพิมพ์เสร็จ Parent ต้องรอ Printer ทุกตัวจบก่อนอ่านผลสุดท้ายและคืนทรัพยากร

หลังจบ โปรแกรมทำลาย semaphore ทั้ง 4 ตัว เรียก munmap และ shm_unlink การ unlink ลบชื่อของวัตถุ ส่วนอายุของพื้นที่จริงขึ้นกับการใช้งานและ mapping ที่ยังเหลืออยู่ การคืนทรัพยากรหลังลูกจบช่วยไม่ให้ทำลาย semaphore ขณะที่ลูกยังใช้อยู่ Linux man-pages shm_open

12.2 เวลาและฟังก์ชันของ engine

Spooler constructor เตรียมข้อมูลด้วย seed 42 จึงเริ่มใหม่แล้วได้งานชุดเดิม ต่างจาก C ที่สุ่มจาก PID และเวลา engine เก็บคิว logs งานที่เริ่มพิมพ์ งานที่เสร็จ Producer Printer และสถานะปิดระบบ

settle() ประมวลผลงานที่พิมพ์เสร็จ Producer ที่พร้อมส่ง การส่ง sentinel เมื่อ Producer จบครบ และการเลือกงานของ Printer ตามลำดับที่กำหนด วนจนไม่มีการเปลี่ยนแปลงที่ทำต่อได้ ณ เวลานั้น

nextTime() หาเวลาถัดไปที่ Printer จะเสร็จหรือ Producer ที่ไม่ได้ถูกบล็อกจะพร้อม step() ข้ามไปเวลานั้นและประมวลผลเหตุการณ์ ส่วน advance(ms) ทำทุกเหตุการณ์จนถึงเวลาปลายทางสำหรับ autoplay หนึ่งขั้นจึงอาจมีหลายเหตุการณ์ และไม่ได้หมายถึงการเพิ่มเวลาทีละ 1 ms

effective() คำนวณ Aging, olderThan() เปรียบเทียบเวลาและ sequence, bestIndex() เลือกงาน, arrivalOrder() จัดภาพตามการเข้าคิว และ selectionOrder() จัดอันดับเลือก ณ เวลาปัจจุบันบนสำเนาคิว ส่วน getter stats ซึ่งอ่านผ่าน sim.stats สรุปข้อมูลจากงานที่เริ่มและเสร็จ

การเล่นอัตโนมัติใช้ requestAnimationFrame แปลงเวลาจริงเป็นเวลาจำลอง จำกัดช่วงต่อเฟรมไม่เกิน 250 ms ก่อนคูณความเร็ว และวาดหน้าประมาณทุก 80 ms เมื่อแท็บอยู่เบื้องหลัง เบราว์เซอร์อาจลดการให้เฟรม ทำให้การเล่นช้าลงได้ ความเร็วการเล่นไม่เปลี่ยนกติกาหรือระยะเวลาจำลองของแต่ละเหตุการณ์

12.3 วิธีอ่านหน้าห้องทดลอง

  • เลือก Printer 1–4 ตัว และเปิดหรือปิด Aging ก่อนเริ่ม เมื่อเริ่มแล้วสองค่านี้ถูกล็อกไว้สำหรับรอบนั้น
  • เริ่มจำลองและเล่นต่อทำให้เวลาเดิน หยุดชั่วคราวเก็บสถานะเดิม ส่วนทีละขั้นขยับถึงเหตุการณ์ถัดไป
  • Reset สร้าง Spooler ใหม่ด้วย seed เดิมและล้างผลรอบก่อน จึงควรจดค่าที่ต้องเปรียบเทียบ
  • แถวลำดับเข้าคิวบอกว่างานที่ยังรอเข้ามาก่อนหลังอย่างไร ตารางเลือกพิมพ์บอกอันดับตามกติกาตอนนี้
  • สีน้ำเงินใช้กับงานปกติ สีส้มแสดงงานที่ effective ลดลงจาก Aging ส่วน STOP เป็น sentinel
  • ป้าย P1–P4 บนกล่อง Producer หมายถึงหมายเลข Producer ต้องแยกจาก P1–P5 ที่ใช้เรียก Priority ของงาน
  • งานเสร็จบนเว็บนับจาก completed จริง ส่วนค่ารอเฉลี่ยบนการ์ดสถิติ ค่าสูงสุด และ Aging นับจากงานที่เริ่มพิมพ์แล้ว แยกจากกราฟสดของงานที่ยังรออยู่ในคิว
  • กราฟสดใช้แกนเวลาคงที่ตลอดรอบ ตั้งแต่ 0 ถึงผลรวมจำนวนหน้าของงานทั้งหมดคูณ 200 ms สำหรับ seed 42 มี 100 หน้า จึงเป็นแกน 0–20 วินาที ความยาวแท่งจึงเปลี่ยนตามเวลารอจริงในหน่วยเวลาจำลอง ไม่ปรับค่าสูงสุดของแกนใหม่ทุกเฟรม
  • Semaphore monitor แสดงภาพหลังเหตุการณ์ ค่า mutex และ stats_lock จึงแสดง 1 ไม่ได้หมายถึงไม่มีการล็อกในโปรแกรม C

เว็บรองรับ WebMCP แบบ optional สำหรับอ่านสถานะและเดินทีละขั้น หากไม่มี API นี้ ปุ่มและตัวจำลองหลักยังใช้งานได้ตามปกติ

12.4 ความเหมือนและความต่างจาก C

ทั้งสองใช้ความจุ จำนวนงาน กติกา Priority/Aging, FIFO ด้วย sequence, เวลาพิมพ์ต่อหน้า การบล็อกคิว และ sentinel แบบเดียวกัน แต่เว็บไม่เรียก fork, mmap หรือ semaphore จริง เหตุการณ์พร้อมกันถูกประมวลผลตามลำดับที่กำหนดไว้ จึงไม่ครอบคลุมทุก interleaving ของระบบปฏิบัติการ

ผลเว็บเหมาะกับการศึกษากติกาและเปรียบเทียบการตั้งค่าด้วยงานชุดเดิม ไม่ใช่ benchmark ของ Linux และไม่จำเป็นต้องได้ตัวเลขตรงกับ C ที่มีการสุ่มและต้นทุนระบบจริง

13.2 คอมไพล์และรัน C

ใช้ Linux หรือ WSL ที่มี GCC และรองรับ POSIX shared memory กับ process-shared semaphore โดยรันจากรากโปรเจกต์

gcc -std=c11 -Wall -Wextra -o spooler_v2 dist/print_spooler_v2.c -pthread -lrt
./spooler_v2
./spooler_v2 2 1
./spooler_v2 1 0

อาร์กิวเมนต์ตัวแรกคือจำนวน Printer ตัวที่สองคือ Aging ตามรูปแบบที่แนะนำ 0 หรือ 1 โค้ดตรวจช่วง Printer แต่ยังใช้ atoi และแปลง Aging ที่ไม่เป็นศูนย์ให้เป็นเปิด จึงไม่ได้ตรวจรูปแบบตัวเลขและตัวเลือกอย่างเข้มงวด

โปรแกรมเริ่มรอบใหม่โดยลบ log เดิมและใช้ shared-memory name คงที่ จึงควรรันทีละ instance ในพื้นที่ทดลอง ไม่ออกแบบสำหรับเปิดหลายรอบพร้อมกัน

13.3 แผนสาธิตในชั้นเรียน

  1. เริ่มด้วย 1 เครื่อง เปิด Aging และอธิบาย Producer คิว และ Printer ก่อนกดทีละขั้น
  2. เลือกงานหนึ่งชิ้นแล้วตาม ID จากเหตุการณ์ส่งงาน ไปคิว ไปเครื่องพิมพ์ และเหตุการณ์พิมพ์เสร็จ
  3. ชี้ความต่างระหว่างแถวเข้าคิวกับตารางเลือกพิมพ์ และอธิบายว่า P1 เป็น Priority สำคัญสูงสุด
  4. เมื่อคิวเต็ม ชี้ Producer ที่รอช่องว่าง แล้วสังเกตว่ากลับมาส่งได้เมื่อ Printer รับงาน
  5. ดูงานรอนานที่ effective ลดลง อธิบายสูตรด้วยตัวอย่าง P5 รอ 8 วินาที
  6. รันจนจบและชี้ SHUTDOWN หนึ่งรายการต่อเครื่องพร้อมการแยกงานเริ่มและงานเสร็จ
  7. Reset แล้วปิด Aging ด้วยงานชุดเดิม เปรียบเทียบตัวเลขและลำดับงาน
  8. Reset แล้วเพิ่มเครื่อง อธิบายว่าหลายเครื่องช่วยพิมพ์พร้อมกันได้ แต่ไม่จำเป็นต้องแบ่งงานเท่ากันหรือเร็วขึ้นเป็นสัดส่วนตรง

กรณีที่เวลา 400 ms ยืนยันว่า #300 เริ่มพิมพ์แล้วและ #400 ยังอยู่ในคิว ส่วนงานที่ Priority กับเวลาเท่ากันใช้ sequence รักษาลำดับ [11,22,33] แม้มีการย้ายงานท้ายอาร์เรย์มาทับช่องที่นำออก คู่มือบนเว็บและ README ได้แก้คำอธิบาย FIFO เดิมให้ตรงซอร์ส พร้อมอธิบายกราฟสดกับสถิติที่บันทึกตอนเริ่มพิมพ์แล้ว

ไฟล์ C harness ยังมี 7 กลุ่มทดสอบ และได้เพิ่มการตรวจ sequence โดยตรงภายในกลุ่มทดสอบ FIFO หลัง swap-last แต่ ยังไม่ได้คอมไพล์และรันในการตรวจรอบนี้ เพราะไม่มี GCC ในสภาพแวดล้อมที่ใช้ จึงไม่อ้างว่าชุดทดสอบ C ผ่าน ต้องนำไปคอมไพล์และรันบน Linux หรือ WSL ที่มี GCC ก่อนยืนยันผล

ชุดทดสอบ JavaScript ครอบคลุมขอบเขต Aging ที่ 1999 และ 2000 ms, ค่าติดลบ, sentinel หลังงานจริง, คิวไม่เกิน 10, งานจริง 20 ชิ้นไม่ซ้ำ, การเล่นกับทีละขั้นให้ผลเหมือนกัน และหลาย Printer ที่บางตัวหยุดขณะอีกตัวพิมพ์งานสุดท้ายแล้ว การตรวจในเบราว์เซอร์ยืนยันว่ากราฟสดเพิ่มตามเวลาจำลอง ขณะที่กราฟเมื่อเริ่มพิมพ์คงค่าเดิมได้จนกว่างานกลุ่มนั้นเริ่มใหม่ และการหยุดชั่วคราวหยุดนาฬิกากับกราฟสดตามคาด

14.3 ข้อจำกัดทางวิศวกรรมของ C

โปรแกรมเหมาะกับงานสาธิต ยังมีการตรวจความผิดพลาดไม่ครบ เช่น sem_init, sem_wait, sem_post และ waitpid ไม่ได้ตรวจผลทุกครั้ง หาก sem_wait ถูก interrupt แล้วเดินต่อโดยไม่ได้สิทธิ์ ความถูกต้องของคิวอาจเสียได้ ควรจัดการ EINTR และ error ตามสัญญาของ API Linux man-pages sem_wait

Parent ไม่อ่าน exit status ลูกอย่างละเอียด ไม่มี cleanup/recovery ครบเมื่อ fork ล้มเหลวหรือ process ตายขณะถือ semaphore และใช้ชื่อ shared memory กับ log คงที่ การพัฒนาต่อควรแยกทรัพยากรต่อ instance จัดการ partial write และแยกตัวนับ started/completed ให้ตรงจังหวะจริง

usleep ใช้จำลองเวลา ไม่ใช่การรับประกัน deadline การพักอาจนานกว่าที่ขอหรือถูก interrupt และ API นี้มีข้อจำกัดด้านความพกพา โดยบางระบบไม่รับค่าตั้งแต่หนึ่งล้านไมโครวินาที ขณะที่งาน 5–8 หน้าของโครงการขอพักตั้งแต่ค่านั้นขึ้นไป ควรพิจารณา nanosleep พร้อมจัดการเวลาที่เหลือเมื่อพัฒนาต่อ Linux man-pages usleep

15 คำถามที่อาจารย์อาจถามพร้อมแนวคำตอบ

15.1 ภาพรวมและโครงสร้าง

ข้อ 1 โปรแกรมนี้แก้ปัญหาอะไร

จำลอง Producer–Consumer ที่ผู้ส่งหลายตัวและผู้รับหลายตัวใช้คิวจำกัดร่วมกัน ต้องป้องกันการแก้ข้อมูลชนกัน ควบคุมคิวเต็ม/ว่าง และเลือกงานตามความสำคัญ

ข้อ 2 โปรแกรมพิมพ์ไฟล์จริงหรือไม่

ไม่ได้พิมพ์จริง ชื่อไฟล์เป็นข้อมูลประกอบงาน การพิมพ์จำลองด้วย usleep ตามจำนวนหน้า ส่วนเว็บใช้เวลาจำลองใน JavaScript

ข้อ 3 มีกี่ process และใช้ thread หรือไม่

มี Parent 1, Producer 4 และ Printer 1–4 รวม 6–9 process เมื่อ fork สำเร็จทั้งหมด ไม่มี pthread_create ในโค้ดนี้

ข้อ 4 ทำไมตัวแปรธรรมดาหลัง fork จึงใช้แทน shared memory ไม่ได้

แต่ละ process มี address space ของตนเอง โปรแกรมจึงสร้าง MAP_SHARED ก่อน fork เพื่อให้ลูกเข้าถึงวัตถุร่วมเดียวกัน ไม่อาศัยการแก้สำเนาตัวแปรธรรมดา

ข้อ 5 close หลัง mmap ทำให้ข้อมูลร่วมใช้ไม่ได้หรือไม่

ไม่ทำให้ mapping หาย descriptor ใช้สร้าง mapping แล้วปิดได้ แต่ mapping ยังอยู่จนยกเลิกด้วย munmap หรือ process จบ

ข้อ 6 ทำไม sem_init ต้องส่ง pshared เป็น 1

เพราะ semaphore ถูกใช้ข้าม process และอยู่ใน shared memory ค่า 0 ใช้สำหรับ thread ภายใน process เดียว ไม่ตรงกับรูปแบบนี้

15.2 คิวและการประสานงาน

ข้อ 7 ทำไมใช้ semaphore ถึง 4 ตัว

แต่ละตัวคุมคนละเรื่อง mutex คุมข้อมูลคิว empty_slots คุมสิทธิ์เพิ่ม filled_slots คุมสิทธิ์นำออก และ stats_lock คุมสถิติร่วม

ข้อ 8 ใช้ mutex อย่างเดียวพอหรือไม่

mutex ป้องกันการแก้พร้อมกัน แต่ไม่ได้บอกว่าคิวเต็มหรือว่าง จึงยังต้องมีกลไกรอเงื่อนไข empty_slots และ filled_slots แทนการวนตรวจคิวตลอดเวลา

ข้อ 9 ถ้าจับ mutex ก่อนรอ empty_slots จะเกิดอะไร

ขณะคิวเต็ม Producer จะถือ mutex รอช่องว่าง แต่ Printer ต้องได้ mutex เพื่อเอางานออก จึงเกิดการรอกันเป็น deadlock ได้

ข้อ 10 คิวเต็มแล้วงานหายหรือไม่

ในการทำงานปกติ Producer รอ empty_slots จนมีช่องคืน ไม่ได้เขียนทับหรือทิ้งงาน เว็บแสดงสถานะ Producer รอช่องว่างเพื่อสื่อพฤติกรรมนี้

ข้อ 11 เหตุใดหลาย Printer จึงพิมพ์พร้อมกันได้ทั้งที่ใช้ mutex เดียว

mutex ครอบเฉพาะการนำงานออกจากคิว Printer ปล่อย mutex ก่อนพิมพ์ จึงทำงานคนละชิ้นพร้อมกันได้โดยยังแก้คิวทีละตัว

ข้อ 12 ทำไมงานที่มาทีหลังอยู่หน้ากว่าในอาร์เรย์ได้

dequeue นำงานท้ายมาแทนช่องของงานที่เลือกออก เพื่อลบโดยไม่เลื่อนทั้งอาร์เรย์ ตำแหน่งเก็บจึงไม่เรียงตามเวลามา แต่การเลือกยังใช้ Priority เวลา และ sequence

ข้อ 13 ถ้าเวลาเข้าคิวเท่ากันยังเป็น FIFO จริงหรือไม่

ซอร์สล่าสุดใช้ enqueue_seq ที่เพิ่มใต้ mutex เป็นตัวตัดสินเมื่อ effective และเวลาเท่ากัน จึงเลือกตามลำดับเข้าคิวสำเร็จ แม้ตำแหน่งอาร์เรย์จะถูกสลับ

ข้อ 14 เหตุใด empty_slots บวก filled_slots จึงไม่จำเป็นต้องเท่ากับ 10 ทุกขณะ

ระหว่าง operation อาจจอง token แล้วแต่ยังไม่ปรับ count หรือยังไม่ post อีก semaphore ความสัมพันธ์จึงต้องพิจารณาช่วงที่ระบบไม่มี operation ค้าง เว็บแสดงค่าหลังเหตุการณ์ ไม่ใช่ทุกจังหวะภายใน C

15.3 Priority และ Aging

ข้อ 15 P1 หรือ P5 สำคัญกว่า

P1 สำคัญกว่าในระดับเดิม โครงการเลือกตัวเลข effective ที่น้อยที่สุด ไม่ได้เลือกเลขมากที่สุด

ข้อ 16 P5 รอ 6 วินาทีมี Priority เท่าไร

Priority เดิมยังเป็น 5 ส่วน effective เป็น 5 - floor(6000/2000) = 2 และสถิติราย Priority ยังนับในกลุ่ม P5

ข้อ 17 effective ติดลบถือว่าเป็น bug หรือไม่

ไม่ใช่ โค้ดไม่ได้จำกัดค่าต่ำสุด เช่น P1 รอ 4 วินาทีได้ −1 งานยังเป็นงานจริง เพราะตรวจ sentinel ด้วย ID ไม่ใช่ effective

ข้อ 18 ทำไมไม่ sort คิวครั้งเดียวตอน enqueue

ค่าหลัง Aging เปลี่ยนตามเวลารอ จึงคำนวณใหม่ตอนเลือก การสแกน O(n) เหมาะกับคิวที่มีงานไม่เกิน 10 ชิ้น

ข้อ 19 งาน P1 ที่เพิ่งเข้าจะแทรกงานที่กำลังพิมพ์หรือไม่

ไม่แทรก ระบบเป็น non-preemptive เครื่องทำงานชิ้นเดิมจนจบ แล้วจึงเลือกใหม่จากงานที่รออยู่

ข้อ 20 ทำไมบางรอบ P5 มีเวลารอเฉลี่ยน้อยกว่า P1

Priority กำหนดการเลือกจากงานที่มีอยู่ตอนเครื่องว่าง ไม่ได้รับประกันอันดับค่าเฉลี่ยทั้งรอบ งานอาจเข้าคนละเวลา ใช้หลายเครื่อง และได้รับ Aging ต่างกัน ต้องดู workload กับสถานะเครื่องประกอบ

ข้อ 21 เปิด Aging แล้วเวลารอเฉลี่ยต้องลดลงหรือไม่

ไม่จำเป็น เป้าหมายคือเพิ่มโอกาสให้งานรอนาน ตัวอย่าง seed42 และ 4 เครื่องในรายงาน เปิด Aging แล้วค่าเฉลี่ยเพิ่ม 10 ms แม้เวลารวมลดลง

ข้อ 22 โครงการนี้พิสูจน์ว่าไม่มี starvation แล้วหรือยัง

ยังไม่ใช่ข้อพิสูจน์สำหรับระบบที่มีงานใหม่เข้าตลอดไป โครงการมีงานจำกัด 20 ชิ้นและเวลาพิมพ์จำกัด จึงจบได้ในการทำงานปกติแม้ปิด Aging การสาธิตแสดงกลไกเพิ่มโอกาสของงานเก่า

15.4 สถิติและการปิดระบบ

ข้อ 23 jobs_done ของ C นับพิมพ์เสร็จจริงเมื่อไร

โค้ดเพิ่มตอน record_stats ก่อน usleep จึงนับงานเริ่มพิมพ์ระหว่างรัน หลัง wait Printer จบครบในการจบปกติจึงเท่ากับงานเสร็จ เว็บแยก started และ completed เพื่อแสดงสถานะสดให้ชัด

ข้อ 24 เวลารอรวมเวลาที่ Producer รอคิวเต็มหรือเวลาพิมพ์หรือไม่

ไม่รวมทั้งสองอย่าง enqueue_ms ประทับหลังได้ช่องและ mutex แล้ว และเวลารอสิ้นสุดที่จุดจับเวลาเลือกงานออกจากคิว เวลาพิมพ์เป็นอีกช่วงหนึ่ง

ข้อ 25 aged_jobs แปลว่าได้พิมพ์เร็วขึ้นจริงกี่งานหรือไม่

ตัวนับบอกจำนวนงานที่ effective ต่ำกว่า Priority เดิมตอนเริ่มพิมพ์เท่านั้น การยืนยันว่าเร็วขึ้นต้องเปรียบเทียบงานชุดเดียวกันกับโหมดปิด Aging

ข้อ 26 ทำไมบางครั้ง log เริ่มพิมพ์มาก่อน log ส่งงาน

enqueue ปล่อยให้ Printer รับงานได้ก่อน Producer เรียก log จึงเป็นผลจาก scheduling และตำแหน่ง logging ไม่ใช่หลักฐานว่างานยังไม่เข้าคิวแล้วถูกพิมพ์

ข้อ 27 ทำไมต้องส่ง SHUTDOWN เท่าจำนวน Printer

แต่ละเครื่องรับหนึ่งรายการแล้วจบ ถ้าส่งไม่ครบ บางเครื่องอาจรอ filled_slots ตลอดไป Parent จึงส่งหนึ่งรายการต่อเครื่องหลัง Producer จบครบ

ข้อ 28 ทำไม sentinel ใช้ INT_MAX และยังต้องตรวจ ID

INT_MAX ทำให้มันมีลำดับหลังงานจริงเมื่อเลือกค่าน้อยสุด ส่วน ID −1 ใช้แยกชนิดงานอย่างชัดเจน ไม่ปะปนกับงานจริงที่ Aging จนได้ effective −1 เว็บใช้ Infinity เพื่อเปรียบเทียบแบบเดียวกัน

ข้อ 29 คิวไม่มีงานจริงแล้วทำลาย shared memory ได้ทันทีหรือไม่

ยังไม่ได้ บาง Printer อาจกำลังพิมพ์งานที่ดึงออกไปแล้ว และยังต้องใช้ Stats กับ semaphore Parent จึงรอทุก Printer จบก่อนรายงานและคืนทรัพยากร

15.5 เว็บ การทดลอง และการพัฒนาต่อ

ข้อ 30 เว็บเรียก fork และ semaphore จริงหรือไม่

ไม่ได้เรียก เว็บจำลองสถานะด้วย JavaScript ส่วน server ส่งไฟล์ static การทดลอง process และ POSIX จริงต้องรัน C แยกบนระบบที่รองรับ

ข้อ 31 กดทีละขั้นหนึ่งครั้งคือเดินเวลาเท่าไร

ข้ามไปเหตุการณ์ถัดไปตาม nextTime เช่น Producer พร้อมหรือ Printer พิมพ์เสร็จ จึงไม่มีระยะคงที่ และเหตุการณ์พร้อมกันอาจเกิดในขั้นเดียว

ข้อ 32 ทำไมผลเว็บกับ C ไม่จำเป็นต้องตรงกัน

เว็บใช้ seed42 และลำดับประมวลผลที่กำหนดเพื่อทำซ้ำได้ C สุ่มจาก PID/เวลาและมี OS scheduling กับต้นทุนการทำงานจริง จึงต่างทั้งชุดงานและเวลาได้

ข้อ 33 เพิ่ม Printer สองเท่าแล้วเร็วขึ้นสองเท่าเสมอหรือไม่

ไม่เสมอ งานมีจำนวนหน้าต่างกันและมาถึงต่างเวลา ยังมีช่วงเลือกคิวร่วมและช่วงปิดระบบ จึงต้องดูผล workload จริง ไม่สรุปจากจำนวนเครื่องอย่างเดียว

ข้อ 34 อธิบายรหัสงานและป้าย Producer อย่างไรไม่ให้สับสน

Job ID เช่น #103 บอก Producer1 เอกสาร index3 หรืองานที่4 ป้าย P1 บนกล่อง Producer บอกผู้สร้างหมายเลข1 ส่วน Priority P1 บอกความสำคัญเดิมสูงสุด ต้องดูบริบทและคอลัมน์ประกอบ

ข้อ 35 ตอนนี้กล่าวว่าชุดทดสอบผ่านทั้งหมดได้หรือไม่

กล่าวได้ว่า JavaScript tests ผ่านครบ21จาก21 และ syntax กับ build ผ่านแล้ว โดยแก้ expected ให้ตรง FIFO ล่าสุดและเพิ่มกรณี Aging ส่วน C harness มี7กลุ่มและเพิ่มการตรวจ sequence หลัง swap-last แล้ว แต่ยังไม่ได้คอมไพล์หรือรันเพราะสภาพแวดล้อมนี้ไม่มี GCC จึงยังกล่าวว่าชุดทดสอบ C หรือทุกส่วนของโครงการผ่านทั้งหมดไม่ได้

ข้อ 36 ถ้าจะพัฒนาให้ใช้งานเชื่อถือได้มากขึ้นควรแก้อะไรก่อน

ตรวจผล API และจัดการ EINTR, ตรวจสถานะการจบของลูก, cleanup เมื่อผิดพลาด, แยก started/completed, จัดการ partial write และใช้ชื่อทรัพยากรต่อ instance รวมถึงออกแบบ recovery เมื่อ process ตายขณะถือ semaphore

ข้อ 37 จะออกแบบการทดลองให้เปรียบเทียบ Aging อย่างเป็นธรรมอย่างไร

ใช้ workload เดียวกันทั้ง Priority จำนวนหน้า และเวลามาถึง เปลี่ยนเฉพาะตัวแปรที่ต้องการศึกษา ทดลองหลายชุดหรือหลายครั้ง และรายงานทั้งค่าเฉลี่ย ค่าสูงสุด การกระจายราย Priority และเวลารวม โดยแยกผลแบบจำลองจากผล C จริง

16 บทสรุปและเอกสารอ้างอิง

โปรแกรมสาธิตการทำงานของหลาย process ที่ใช้คิวจำกัดร่วมกัน โดย semaphore แบ่งหน้าที่ควบคุมข้อมูลและเงื่อนไขคิว ส่วน Priority/Aging กำหนดว่างานใดจะได้พิมพ์เมื่อเครื่องว่าง ซอร์สล่าสุดรักษา FIFO ในกลุ่มที่ effective เท่ากันด้วยเวลาและ sequence และใช้ sentinel ปิด Printer ให้ครบก่อนคืนทรัพยากร

การอธิบายโครงการควรยึดความหมายของข้อมูลให้ตรงกัน โดยแยก Job ID, Producer, Priority เดิม, effective, ตำแหน่งอาร์เรย์, ลำดับเข้าคิว และลำดับเลือกงาน รวมทั้งแยกงานเริ่มพิมพ์กับงานเสร็จและผลเว็บกับผลระบบปฏิบัติการจริง
